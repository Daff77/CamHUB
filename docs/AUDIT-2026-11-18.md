# Audit CamHUB — 18 November 2026

Audit mencakup kondisi working tree saat diperiksa, termasuk perubahan lokal yang belum di-commit. Kode produk tidak diubah. Pemeriksaan berupa penelusuran kode, 87 unit test bawaan, dan reproduksi terisolasi menggunakan direktori sementara serta metode handler yang diekstrak melalui AST. Kamera fisik, tunnel publik, dan browser tidak diuji secara langsung.

## Temuan

### 1. P1 — File proyek dapat diakses melalui static fallback

Lokasi: `server.py:204–213`.

Jika file tidak ditemukan di `web/`, `translate_path` mencari path yang sama di root proyek. Permintaan `/config/services_config.json` akan memilih file konfigurasi asli. Source code, README, dan artefak lain di root juga dapat terekspos. README memuat kredensial kamera, sehingga dampaknya mencakup kebocoran rahasia. Server bind ke `0.0.0.0` pada baris 1277 dan proyek mendukung tunnel.

Bukti: pemanggilan metode yang diekstrak tanpa mengimpor server mengembalikan path konfigurasi asli. Pengujian tidak membaca atau mencetak isi rahasia.

Perbaikan: layani static hanya dari `web/`; akses media melalui endpoint khusus dengan validasi path. Rotasi kredensial yang pernah tersimpan dalam dokumen/config yang terekspos dan pindahkan rahasia ke penyimpanan khusus.

### 2. P1 — Otorisasi admin dapat dipalsukan dan banyak operasi tidak dilindungi

Lokasi: `server.py:215–227`, `server.py:896`, `server.py:1229`.

Header `X-CamHub-Role: admin` langsung disetujui. Setiap string dengan awalan `Bearer ` juga diterima tanpa memeriksa token. Sebagian besar operasi start/stop kamera, PTZ, cleanup, serta penghapusan rekaman/event tidak memanggil pemeriksaan admin sama sekali. Kepercayaan pada loopback juga tidak dapat membedakan pengguna lokal dari request yang diteruskan proxy lokal seperti ngrok.

Bukti: metode menerima role admin buatan dan `Bearer invalid` dari alamat non-loopback. Penelusuran handler menunjukkan guard hanya pada operasi diagnostics tertentu.

Perbaikan: autentikasi sesi/token yang diverifikasi server, pemeriksaan izin terpusat untuk seluruh endpoint, serta pembatasan origin. Role dari UI tidak boleh menjadi bukti otorisasi.

### 3. P1 — Storage manager dan recording manager memakai skema indeks berbeda

Lokasi: `core/recording_manager.py:254–303`, `core/storage_manager.py:451`, `core/storage_manager.py:669–705`, `server.py:693`.

Recording manager menyimpan `filePath` dan `fileName`; storage manager membaca/menulis `path` dan `filename` pada file indeks yang sama. Reindex mendeteksi file yang sebenarnya sudah ada sebagai entri baru, lalu menimpa entri dengan skema berbeda. Setelah indeks tersebut dimuat kembali, playback mengakses `item['filePath']` yang sudah hilang. Cleanup juga menggunakan path kosong untuk entri asli sehingga targetnya dapat menjadi direktori root, bukan file rekaman.

Bukti: reproduksi membuat satu segmen melalui scanner recording manager lalu menjalankan reindex. Hasil `recordingsReconciled = 1` dan `filePath` tidak lagi ada pada indeks disk.

Perbaikan: satu skema dan satu pemilik penulisan indeks, migrasi entri lama, serta pengujian integrasi record → reindex → reload → playback → retention.

### 4. P2 — ID kamera yang mengandung underscore terpotong

Lokasi: `core/recording_manager.py:260–261`.

ID diambil dari `filename.split('_')[0]`. Konfigurasi menggunakan `okam_1`, `okam_2`, dan `okam_3`; ketiganya menjadi `okam`. Filter rekaman berdasarkan kamera asli tidak menemukan rekaman yang sesuai dan pemisahan metadata antarkamera hilang.

Bukti: file di direktori `recordings/okam_1/...` menghasilkan `cameraId = okam`.

Perbaikan: ambil ID dari direktori kamera atau metadata sesi, bukan pemisah nama file.

### 5. P1 — Perlindungan rekaman aktif dan playback tidak berlaku konsisten

Lokasi: `server.py:1178–1182`, `core/storage_manager.py:426–427`, `core/storage_manager.py:459`, `core/storage_manager.py:779`, `core/recording_manager.py:400–439`.

Endpoint cleanup mengirim direktori sesi sebagai daftar file aktif, tetapi evaluator membandingkannya dengan path file secara persis. Cleanup otomatis tidak mengirim daftar sesi aktif. Recording manager juga menjalankan retention sendiri tanpa memeriksa playback lock maupun sesi aktif. Akibatnya perlindungan yang ada pada storage manager dapat dilewati oleh jalur penghapusan lain ketika umur atau kuota memicu retention. Di Windows penghapusan file terbuka dapat gagal; di platform lain file dapat terhapus saat masih dipakai.

Perbaikan: pusatkan retention dan pemeriksaan lock, gunakan path segmen aktual, dan perpanjang lease sepanjang playback/download berlangsung. Uji seluruh jalur cleanup, bukan evaluator saja.

### 6. P2 — Indeks dihapus walaupun penghapusan file gagal

Lokasi: `core/recording_manager.py:442–465`, `core/storage_manager.py:595–623`.

Recording manager menghapus metadata sebelum mengetahui apakah file berhasil dihapus; helper menelan exception. Storage manager menambahkan ID ke daftar metadata yang akan dihapus bahkan setelah `os.remove` gagal. API dapat melaporkan sukses sementara file masih memenuhi disk; scanner berikutnya dapat memunculkannya kembali.

Perbaikan: helper penghapusan mengembalikan hasil eksplisit, metadata hanya dihapus setelah keberhasilan atau konfirmasi file sudah tidak ada, dan respons membedakan keberhasilan penuh dari kegagalan parsial.

### 7. P2 — HTTP Range salah untuk suffix dan rentang di luar ukuran file

Lokasi: `server.py:276–296`.

`Range: bytes=-500` ditafsirkan sebagai byte 0 sampai 500, bukan 500 byte terakhir. Start yang melewati EOF atau start lebih besar dari end tidak ditolak dan dapat menghasilkan Content-Length negatif. Ini dapat mengganggu seek/playback klien yang memakai rentang tersebut.

Perbaikan: implementasikan suffix/open-ended range dan kembalikan 416 untuk rentang tidak valid; tambahkan pengujian dengan file sementara.

## Validasi dan keterbatasan

- `python -m unittest discover -s tests -v`: 87 tes lulus, 13,628 detik.
- Tes memunculkan peringatan subprocess yang belum selesai dan log AI gagal membaca image fixture. Ini tidak menggagalkan suite, tetapi menunjukkan perlunya isolasi fixture/background worker yang lebih baik.
- Reproduksi tambahan membuktikan empat mekanisme: static fallback, header admin palsu, pemotongan ID kamera, dan perubahan skema indeks setelah reindex.
- Temuan retention dan HTTP Range berasal dari penelusuran kode; tidak dilakukan penghapusan data pengguna maupun percobaan pada kamera aktif.
- Kelulusan unit test belum mencakup integrasi antar-manager yang menjadi sumber beberapa temuan utama.
